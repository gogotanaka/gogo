# 0013: `@gogo book` メンション追加・板情報への出来高表示・発注上限引き上げ

## Status

Accepted (2026-08-19)

## Context

`docs/adr/0012` の自動再ログインに続き、同じセッションで3つの小さな変更を行った。
いずれも既存の設計（メンションコマンドの厳密パース、Slack投稿フォーマット、
安全弁としての上限金額）の上に乗る追加的な変更で、新しいアーキテクチャ上の
決定は伴わないため、まとめて1件のADRとして記録する。

また、このタイミングで本アプリのADR置き場をリポジトリルートの `docs/adr/`
（`0001`〜`0012`、内容はすべてsbi-order専用）から、このアプリ配下の
`apps/sbi-order/docs/adr/` へ移動した（`git mv`で履歴を保持）。ルートの
`docs/adr/` は元々sbi-order以外の内容を想定していなかった実態に合わせ、
アプリのドキュメントはアプリ配下に置く方針にした。以後のsbi-order関連ADRは
このディレクトリに追加していく。

## Decision

### 1. `@gogo book` メンションコマンド

板情報の定期投稿（8〜12分間隔）を待たずに、その場で板情報を取得して投稿できる
ようにした。`mention_listener.py` に `parse_book()` を追加し、`book`
（`SBI_WATCH_TICKERS`全部）または `book 3930`（銘柄指定）を解析する。
既存の `buy`/`sell`/`clear all` と同じ厳密パース方針（曖昧な自然文解析はしない、
`books` のような部分一致もしない）を踏襲した。`web.py` 側は `_on_book_request`
（受付・キュー投入のみ、HTTPリクエストのスレッドで実行）と
`_process_book_request`（実際の取得・投稿、`_sbi_loop`スレッドで実行）に分離
しており、他のコマンドと同じ非同期処理パターンに合わせている。

### 2. 板情報投稿に本日の出来高（株数）を追加

`get_order_book()` が読む個別銘柄ページには、板情報のテーブルと同じページ内に
出来高セル（`#MTB0_5 .fm01`）が既に存在することを実画面で確認した
（`get_price`が使っている`#MTB0_0`と同じテンプレート構造）。追加のページ遷移
無しに、同じページ読み込みの中でこれもあわせて読むようにした。戻り値を
`[{...}, ...]`（板の行のリスト）から `{'rows': [...], 'volume': str|None}`
に変更し、`format_order_book()` はヘッダに「（本日出来高: N株）」を付与する。
出来高が読めなかった場合でも板情報自体は失敗させない（`volume: None`のまま
返す）。定期投稿・`@gogo book` の両方の経路に反映される。

### 3. メンション発注の上限金額を引き上げ

`SBI_MAX_ORDER_VALUE_YEN` を50万円から500万円に変更（ユーザー指示）。
`config/.env`（gitignore対象）のみの変更で、コード変更は無い。

## Verification

- `get_order_book('3930')` を実行し、`volume: '32,200'` が実際に取得できる
  ことを確認。`format_order_book()` の出力にヘッダとして反映されることも確認
- `parse_book()` の単体テスト: `book` / `Book`（大文字小文字無視）/ `book 3930`
  （銘柄指定）が一致し、`books`（部分一致）は一致しないことを確認
- `@gogo book` の実際のSlack上での動作（メンション送信→投稿）は未確認
  （パースと取得処理はそれぞれ個別に確認済みだが、Events API経由の
  エンドツーエンドはまだ）

## Consequences

- ADRの置き場が変わったことで、今後このアプリの変更を追う際は
  `apps/sbi-order/docs/adr/` を見ればよくなった（ルートの`docs/adr/`は見なくてよい）
- 板情報のデータ構造が変わった（リスト→辞書）ため、`best_bid()` など
  `get_order_book()` の戻り値に依存する既存コードもあわせて修正した
  （`row["rows"]`経由でアクセスするように変更）
- 発注上限が10倍になったことで、誤入力時の実害も大きくなりうる。上限は
  あくまで「明らかな誤入力・暴走の歯止め」であり、金額そのものの妥当性を
  判断するものではない点は変わらない
