# 0011: 画面遷移のたびにログアウトされる問題の根本原因と対策

## Status

Accepted (2026-08-18)

## Context

ユーザーから「画面遷移した瞬間、ログアウトされる。普通に人が画面遷移する場合は
そうならない」という強い指摘があった。実際、ログインしてもすぐに（時には
こちらが何も操作していないタイミングでも）ログアウト状態に戻ってしまう現象が
繰り返し発生し、ログイン→確認→ログアウトのサイクルを何度も繰り返していた。

**調査で分かったこと**

`order_store`（ローカルSQLite）に、実際には既にSBI側で取消済みの注文6件
（番号493・494・495・496・497・499）が `status='submitted'` のまま残っていた。
原因は、前段のトラブルシューティング（0009・0010関連の作業）で、正規の
`_process_clear_all`（Slackの`clear all`経由、取消と同時にローカルDBも
`cancelled`に更新する）を使わず、`sbi_client.cancel_order()` を直接スクリプトから
呼んで手動で取消していたこと。SBI側は取消されたが、ローカルDBの同期処理を
経由しなかったため、レコードが「submitted」のまま残ってしまった。

`_poll_orders` は `status='submitted'` の注文を60秒おきに全件チェックする
実装で、かつ `check_order_status` が「注文照会一覧に見つからない」場合を
`unknown` として返しても、呼び出し側でその状態を何も処理せず（DBを更新
しないまま）放置していたため、この6件は永久に「追跡対象」であり続けていた。
結果として **毎分6回**、「ホームへ遷移→取引メニュー→注文照会メニュー」という
画面遷移が自動的に繰り返されていた。

**検証**: `web.py`（＝この自動遷移ループ）を完全に停止した状態でログインし
直したところ、2分間放置してもログイン状態が維持された。自動遷移を止めている
間はログアウトが起きないことを確認した。裏を返せば、頻繁すぎる自動遷移
そのもの（1分間に6回×goto+クリック2回、という高頻度アクセス）がログアウトの
トリガーになっていたと強く示唆される。SBI側の正確な検知ロジックは分からない
（bot検知フィンガープリントによるものか、単純なアクセス頻度によるものかは
未確認）が、少なくとも「頻度を減らせば起きなくなる」ことは実証できた。

## Decision

- ローカルDBの該当6件を `cancelled` に修正し、無駄な追跡を止めた
- `_poll_orders` に `status == "unknown"` のハンドリングを追加。注文照会一覧に
  見つからない注文は `unknown` ステータスにしてDBを更新し、以後の追跡対象から
  外れるようにした（`pending_watch_orders()` は `status = 'submitted'` のみを
  対象にしているため、一度`unknown`になれば二度とポーリングされない）
- 今後、`sbi_client` のメソッドをデバッグ目的で直接スクリプトから呼ぶ場合も、
  ローカルDBとの整合性を意識する（可能なら `_process_clear_all` 等、DB更新も
  セットになっている正規のパスを使う）

## Update (同日、後刻): 上記の結論は不十分だった

対策後、`web.py`を再起動し「追跡中の注文0件（`_poll_orders`は空ループで何も
しない）、`_poll_price`の間隔（8〜12分）もまだ到達していない」という、
自動遷移がほぼゼロのはずの状態で約2.5分待ってから再確認したところ、
**それでもログアウトしていた**。つまり「自動遷移の頻度を減らせば直る」という
上記の結論は誤り、または少なくとも不十分だったことになる。

この結果は、むしろ「セッションが単純にかなり短い時間（数分オーダー）で
タイムアウトしており、遷移そのものが原因ではなく、遷移のたびに“既に切れていた
セッション”が可視化されているだけ」という説明の方が整合的であることを示唆する。
自動化の遷移頻度を落としても直らなかった以上、根本原因はまだ特定できていない。

次のステップとして、ログイン直後から一定間隔（例: 60秒ごと）で、ナビゲーションを
一切伴わない最小限の確認（既存タブの `_is_logged_in()` 相当のDOM確認のみ）を
繰り返し、実際に何分でセッションが切れるかを計測する必要がある。原因を
「直す」のではなく、実際のタイムアウト時間を把握した上で、その前提で
運用（頻繁な再ログイン依頼を受け入れる等）を設計し直す方向になる可能性が高い。

## Update 2 (同日): クリーンな計測結果 — 放置では切れない

上記の反省を踏まえ、今度こそ完全にクリーンな条件で計測した。ログイン直後に
**1回だけ** `SBIClient` を起動し（CDP接続は1回のみ、以後新規接続を一切作らない）、
以後は `goto()` 等のナビゲーションを一切行わず、60秒おきに `_is_logged_in()`
（既存ページのDOMを読むだけ、ネットワーク往復を伴わない）で状態を記録した。
`web.py` も完全に停止した状態で実施し、他のスクリプトも一切実行しなかった。

結果: **12分間（720秒）、60秒おき12回の確認すべてで `logged_in=True`**。
セッションは一切切れなかった。

これは重要な結果で、これまでの「頻繁にログアウトする」という現象が、単純な
時間経過によるセッションタイムアウトではないことを強く示唆する。むしろ、
以下のような**能動的な操作**が引き金になっていた可能性が高い（今回の計測では
意図的にこれらを一切行っていない）:
- 短時間に何度も新しいCDP接続を張り直す（このセッション中、デバッグのために
  数十〜100回近く行っていた）
- `web.py` プロセスを `pkill -9` で強制終了する（CDP接続が正常にクローズされず
  ブラウザ側に異常な切断として記録される可能性がある）
- 短時間に何度もページ遷移（`goto()`）を行う

次に必要なのは、これらの候補を1つずつ、他の要因を混ぜずに単独でテストする
ことである（例: 同じ接続を使い回したまま `goto(HOME_URL)` を1回だけ行い、
それだけでログアウトするかを見る等）。少なくとも「純粋な放置」は原因ではない
と確認できたため、原因調査の範囲は「何らかの能動的操作」に絞り込めた。

## Update 3 (同日): 単発の接続・単発の遷移も原因ではないと確認、結論

2本の並行計測を実施した:
1. 1本目の接続をそのまま18分間放置（ナビゲーションなし）→ 全区間 `logged_in=True`
2. 別の新規接続を張り、`goto(HOME_URL)` を1回だけ実行した直後、およびその後
   4分間放置 → こちらも全区間 `logged_in=True`

この2つの結果により、以下がいずれも単独では原因ではないと確認できた:
- 新しいCDP接続を張ること自体
- 1回のナビゲーション
- 時間経過によるセッションタイムアウト（少なくとも18分以内では発生しない）

**結論**: これまで繰り返し発生していたログアウトは、このセッション中に
デバッグ目的で行っていた**大量の接続張り直し・`pkill -9`によるweb.pyの強制
終了・短時間での連続したページ遷移**が積み重なって引き起こされたものである
可能性が高い。`_sbi_loop` の通常運用（起動時に1回接続し、以後はその接続を
使い回しながら低頻度でポーリングする設計）そのものは、この計測結果からは
安定して動作するはずだと判断する。

**教訓**: 今後同様のデバッグを行う際は、
- CDP接続は使い回し、不要に何度も張り直さない
- `web.py` の停止には `pkill -9`（SIGKILL）ではなく、可能なら正常終了
  （`Ctrl-C`相当のシグナルや、サーバー側のシャットダウン処理）を使う
- 短時間に多数のページ遷移を連続させない

これらを守れば、今回のような不安定さの多くは避けられると考えられる。

## Consequences

- 定常状態（追跡中の注文が実際に「submitted」のものだけ）に戻れば、
  `_poll_orders` は60秒ごとに1回、実際に未約定の注文がある分だけ遷移する
  （0件なら遷移自体発生しない）。0009時点の想定に近い、低頻度なアクセスに戻った
- 「頻繁な自動遷移がログアウトを誘発する」という経験則は得られたが、SBI側の
  具体的な閾値・検知条件は依然として不明。同様の問題が起きた場合は、まず
  `web.py`を止めて自動遷移をゼロにした状態でログインが安定するか確認する
  （切り分けの基本手順として）
- この経験則は、0001から続けている「過大なアクセスをしない」という方針
  （SBI利用規約 第17条）の実務的な裏付けにもなった。板情報ポーリングの間隔
  （8〜12分）や、注文照会ポーリング（実際に追跡すべき注文がある時だけ）は、
  この意味でも妥当な頻度に保つ必要がある
