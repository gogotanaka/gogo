# 0016: HTTPスレッドと_sbi_loopの並行性ガード

## Status

Accepted (2026-08-20)

## Context

このアプリは「Playwrightに触る唯一のスレッド `_sbi_loop`」と「Slackイベント/
web UIを受けるHTTPスレッド（ThreadingHTTPServer、リクエスト毎スレッド）」の
2種類が並走する。設定（watches.json）・注文記録（orders.db）はその間の共有
状態で、1回のリビッドティックは板取得・照会・取消・発注のページ遷移で数十秒
かかるため、「ティック実行中に設定が変わる」交錯は現実に起きる。

2026-08-20 の多角レビューで、旧セッション実装にこの交錯起因の確定バグが
複数見つかった（ティック途中のセッション置き換えで旧銘柄の気配価格のまま
新銘柄を発注する・停止確認の返信後に発注が走る・発注記録が別セッションに
紐づく等）。

## Decision

方針: **HTTPスレッドは「設定ファイルを書く」ことしかせず、売買の判断・実行は
すべて `_sbi_loop` の中で、実行直前に設定を読み直して行う。**

- 設定の書き込み（`watch_store`）はロック + tmp→rename の原子的書き込み。
  読み書きの単位でしか直列化しない（ティック全体をロックで覆わない）
- ティックは発注の直前に `still_valid()`（設定を読み直して開始時点の設定と
  同一か、`updated_at` 含む dict 比較）を確認し、変更・解除されていれば発注を
  中断する。取消フェーズ後の中断なら「取り消しただけ」で終わり、新しい設定の
  ティックが数秒内に置き直すので実害はない
- 新規設定・置き換えの即時反映は、キュー渡しではなく `_sbi_loop` 側が
  `updated_at` の変化を監視して行う（HTTPスレッドからの kick キューは
  定期スケジュールと二重実行の競合を作った実績があるため使わない）
- 価格上限超えの一回だけ通知フラグ（`_cap_alerted`）と web UI 表示用の
  `_loop_state` は `_sbi_loop` だけが書く。HTTPスレッドは読むだけ
- 一回きりの注文（buy/sell）と clear-all は従来どおり `_work_q` 経由で
  `_sbi_loop` に直列化する

## Consequences

- 「返信内容と実際の動作が食い違う」系のレースは、発注直前の再確認で
  金銭が動く方向には倒れなくなった（最悪でも「取消だけして発注しない」）
- 設定変更の反映は最大1ループ（約1秒）+ ティック実行時間の遅延
- watches.json を人手で直接編集しても同じ経路で安全に反映される
