# 0004: 実画面でのセレクタ確認とPlaywrightスレッド問題の修正

## Status

Accepted (2026-08-17)

## Context

0003でCDP接続に切り替えた後、ユーザーが実際に普段のChromeでSBI証券にパスキーログイン
してくれたので、そのセッションに接続して `sbi_client.py` のプレースホルダーセレクタを
実物に合わせて修正した。あわせて、動作確認中に `web.py` の並行処理設計に実装バグが
見つかったので、そちらも修正した。

## Decision

**実画面確認（読み取り専用の操作のみ、実発注はしていない）**

- `_is_logged_in`（「ログアウト」表示の有無）は仮実装のままで正しく動作することを確認
- `get_price`: トップページの銘柄検索ボックス（`#brand-search-text`）に銘柄コードを
  入力してEnterで検索し、遷移先の現在値セル（`#MTB0_0 .fxx01`）から取得する方式に
  実装。はてな(3930)で実際に「734」を取得できることを確認した。現在値セルは検索直後
  「--」(未取得)から非同期に更新されるため、`networkidle`待ち（このページは自動更新の
  常時接続がありずっと発火しない）ではなく、値が変わるまで短間隔でポーリングする方式にした
- `check_order_status`: 「取引」→「注文照会」とクリックして注文一覧テーブルに辿り着く
  ことを確認。列0=注文番号、列1=注文状況、列5=取消/訂正リンクという構成を実際の注文
  （番号485・486、はてな現物買300株）で確認した。当初、行全体のテキストに「取消」という
  文字列が含まれるかで状態判定していたが、これは取消/訂正の操作リンクが常に表示されている
  ことに起因する誤判定（実際は「注文中」なのに「cancelled」と誤検知）だったため、列1
  （注文状況セル）だけを見るよう修正した
- `place_order`: 「取引」画面に埋め込まれた発注フォームの実フィールド名を確認し反映した
  （`stock_sec_code` / `trade_kbn`(0=現物買,1=現物売) / `input_quantity` /
  `in_sasinari_kbn`(' '=指値) / `input_price` / `hitokutei_trade_kbn`(0=特定預り) /
  `selected_limit_in`(this_day=当日中) / 取引パスワードは `#pwd3`。同名の隠しダミー
  フィールド pwd1/pwd2/pwd4 が並んでいるため id 指定が必須）。スクリーンショットで
  入力結果が正しいことを目視確認した。フォーム送信後の「注文確認画面へ」ボタンより先
  （確認画面・最終発注ボタン・注文番号取得）は、本物の注文が発注されるリスクがあるため
  クリックせず、`HumanInterventionRequired` を投げて安全に停止する設計のまま残した
- ナビゲーションの実装上の注意点: このサイトは同じテキストのリンクが複数箇所（非表示の
  テンプレート複製や、bounding boxを持たない要素）に存在し、`get_by_role(role="link",
  name=X, exact=True)` によるアクセシブルネーム一致が信頼できない場面が多い。そのため
  `_click_visible_text()` という共通ヘルパーを追加し、`get_by_text` で全マッチを取った上で
  実際に bounding box を持つ（＝画面に表示されている）要素だけをクリックするようにした
- 各ページのURLはセッション固有のトークン（`_SeqNo`等）を含み `goto()` で再現できないため、
  `HOME_URL` から毎回リンクをクリックして辿る設計にした（0003時点の想定通り）

**`web.py` の並行処理バグ修正**

- 発注ワーカー・注文ポーラー・株価ポーラーをそれぞれ別スレッドにし、共有の `SBIClient`
  シングルトンを介して同じPlaywright接続を使い回す設計だったが、Playwrightの同期APIは
  生成したスレッド以外から呼ぶと `Cannot switch to a different thread`
  （greenlet実装に起因）で壊れることが実行時に判明した
- 修正として、SBI/ブラウザとのやり取りを行うのは `_sbi_loop` という単一のスレッドだけに
  限定した。発注キュー（`queue.Queue`）の処理、約定確認（60秒間隔）、株価投稿
  （20〜30分間隔）を全部この1スレッドのループ内で順番に処理する。HTTPサーバ側の
  スレッドは `order_store`（SQLite）と `_work_q` の read/write だけを行い、
  Playwrightオブジェクトには一切触れない

## Consequences

- `place_order` は「発注フォームへの入力」までは実環境で検証済みだが、実際に注文が
  発注されるところまでは未検証のまま。使う前に、必ず一度は人間が手動で最後まで操作して
  `sbi_client.py` を完成させる必要がある（README参照）
- ナビゲーションを `_click_visible_text` に統一したことで、今後SBI側の画面構成が変わった
  場合も、同じ壊れ方（非表示要素への誤クリック）はしにくくなった。ただし依然として
  DOM構造依存であり、SBI側の改修で壊れる可能性は残る
- 並行処理を1スレッドに統合したことで、発注処理・約定確認・株価取得は互いに直列化される
  （同時には走らない）。頻度が既知の値（60秒・20〜30分・都度の発注）である現状の
  スケールでは、これによる実用上の遅延は無視できる範囲と判断した
