# 0003: sbi-order のブラウザ接続を CDP 経由の実ブラウザ利用に変更

## Status

Accepted (2026-08-17)

## Context

0001/0002 では Playwright が自動化専用のまっさらなブラウザプロファイル
（`launch_persistent_context`）を立ち上げ、その中で ID/パスワードによるログインを
自動化する設計にしていた。

実際に動かそうとしたところ、ユーザーから「パスキーだからいつも使ってるブラウザで
ログインしたい」という指摘が出た。パスキー（WebAuthn）はブラウザのプロファイル
（あるいはmacOSのプラットフォーム認証器・iCloudキーチェーン等、ブラウザの
サインイン状態）に紐づいており、Playwrightが新規に立ち上げるまっさらな
プロファイルには存在しない。そのため、そのプロファイルではそもそもパスキーで
ログインできない。

## Decision

- `SBIClient` は自前でブラウザを起動するのをやめ、`playwright.chromium.connect_over_cdp()`
  でユーザーが普段使っているブラウザ（リモートデバッグ有効で起動し直したもの）に接続する
  方式に変更した。`apps/mf-pl/send_slack.py` がSlackに対して使っているCDPフォールバックと
  同じ発想
- ログインは常に人間が普段のブラウザで（パスキーで）行う。自動ログイン（ID/パスワード）は
  廃止した。`ensure_logged_in` はログイン状態を確認するだけで、未ログインなら
  `HumanInterventionRequired` を投げて Slack 経由で人間を呼ぶ（0002の仕組みをそのまま使う）
- `SBI_USER_ID` / `SBI_LOGIN_PASSWORD` の設定は不要になった。`SBI_CDP_URL`
  （既定 `http://localhost:9223`）を追加した
- 接続先ポートは、同一マシン上で既に `apps/mf-pl` がSlackのCDPに `9222` を使っているため、
  衝突を避けて `9223` にした

## Consequences

- パスキーログインが実際に機能するようになった代わりに、普段使っているブラウザを
  `--remote-debugging-port` 付きで起動する必要がある。この間、同じ端末上の他のプロセスも
  そのポートに接続すればブラウザを操作できてしまう（対象タブに限らず、他のタブ・
  ログイン中の別サービスも含めて）。共有端末や信頼できないプロセスが動く環境では
  避けるべきというリスクを、README に明記した
- `SBIClient.stop()` は接続を切るだけで、ブラウザ本体は `close()` しない
  （間借りしているだけなので、閉じるとユーザーの実ブラウザが終了してしまう）
- 0001で書いていた「セッションが切れたら自動で再ログインを試みる」という前提はそもそも
  無くなった（元々パスキーなので自動再ログインはできない）。切れたら常に人間を呼ぶ、
  という0002の設計とちょうど整合する形になった
