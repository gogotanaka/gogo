# 0010: `_sbi_loop`の異常終了対策と、ブラウザタブのクラッシュ自動復旧

## Status

Accepted (2026-08-18)

## Context

ユーザーから「Slackに通知が来ない」という報告があり、調査したところ2つの独立した
問題が重なっていたことが分かった。

**問題1: `_sbi_loop`がエラーで無言で落ちる**

`web.py`の起動処理で `client = SBIClient().start()` が例外（今回はCDP接続の
タイムアウト）を投げた際、この呼び出しが try/except で囲まれていなかったため、
`_sbi_loop`スレッド全体が例外で終了していた。HTTPサーバ自体は別スレッドで動き
続けるため、Slackのメンションには「受け付けました」と即座に返信されるが、
実際の発注処理・約定確認・板情報投稿は一切行われない、という気づきにくい
壊れ方をしていた（プロセス自体は生きているように見える）。

**問題2: ブラウザのタブが実際にクラッシュしていた**

ユーザーが `buy 3930 100 700` を連続して素早く何度もテストした際、Chromeの
タブが実際に「Aw, Snap! (Error code: 5)」でクラッシュした。ログには
`Locator.count: Target crashed` というエラーが複数の注文について連続して
出ており、`ensure_logged_in`以降の全操作が同じ理由で失敗し続けていた
（自動復旧の仕組みが無く、手動でブラウザを見て気づくまで直らない）。

さらに復旧作業中、CDPの生のHTTPエンドポイント（`/json/version`, `/json/list`）は
応答するのに、Playwright経由の接続だけがハングするという状態にも遭遇した。
このセッション中に数十回CDP接続・切断を繰り返したことでChrome側のDevTools
セッションが詰まったのが原因とみられ、Chromeの完全な再起動でしか解消しなかった。
Chrome再起動によりパスキーのログインセッションも失効したため、再ログインが
必要だった。

## Decision

- `web.py` に `_connect_with_retry()` を追加。`SBIClient().start()` が失敗しても
  例外を外に投げず、10秒間隔でリトライし続ける（1回目とそれ以降5回に1回、
  Slackにログイン依頼のメンションを送る）。これにより起動時の接続失敗で
  スレッドが二度と回復しない状態を防ぐ
- `_sbi_loop` のメインループ本体（キュー処理・ポーリング）も try/except で
  包み、想定外の例外が起きてもログに出すだけでループ自体は継続するようにした
- `sbi_client.py` に `_page_is_alive()`（`page.evaluate("1")`が通るか）と
  `_recover_crashed_page()`（同じブラウザコンテキスト内に新しいタブを開いて
  クラッシュしたタブと差し替える）を追加。`ensure_logged_in()`
  （ほぼ全操作の起点）の先頭で毎回タブの生存確認を行い、死んでいれば
  自動的に新しいタブに切り替えてから処理を続ける

## Consequences

- タブが再びクラッシュしても、次の操作時に自動で新しいタブに切り替わり、
  ログイン状態の再確認（必要ならSlackでの依頼）を経て自律的に復旧するように
  なった。ただしCookieはブラウザプロファイル単位で保持されるため、新しいタブ
  でもログインセッション自体は通常引き継がれる想定（今回は別要因＝Chrome
  自体の再起動でセッションが切れた）
- `_sbi_loop`が「無言で落ちて何も処理しない」状態には陥らなくなったが、
  裏を返すと「動いているように見えて実は全く機能していない」状態を今後
  見逃さないためには、ログ（`[startup]`, `[sbi_loop]`プレフィックス）を
  定期的に確認する運用がまだ必要
- CDP接続を極端に頻繁に張り直す（今回のような対話的デバッグで数十回、等）と
  Chrome側のDevToolsセッションが詰まる場合があると分かった。今後同様の
  デバッグをする際は、1つの接続を使い回す・不要になった接続は明示的に
  `stop()`する、といった配慮が望ましい
- 実運用上の連続メンション送信（同じコマンドを間隔を空けずに何度も送る）は
  ブラウザに負荷をかけクラッシュを誘発しうる。上限（`SBI_MAX_ORDER_VALUE_YEN`）
  はあるが、連続実行そのものを抑制する仕組みは無いままなので、今後レート
  制限が必要になる可能性がある
