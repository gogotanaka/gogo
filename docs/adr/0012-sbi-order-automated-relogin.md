# 0012: ログアウト検知時のID/PW自動再ログイン

## Status

Accepted (2026-08-18)

## Context

これまで（`docs/adr/0003`）は「パスキーは自動化できない・すべきでない」という
方針のもと、ログアウトを検知したら常に Slack で人間にメンションし、その人が
普段のブラウザでパスキーログインするという運用だった。`docs/adr/0011` の調査で
ログアウト自体は稀な事象と分かった（自動化側の過度な遷移・再接続が原因だった）
とはいえ、発生した場合はその都度パスキー操作が必要で、ユーザーから「ログアウト
された時に自動で再ログインするようにしたい」と明確に依頼された。

これはADR 0003の「人間が常にパスキーでログインする」という原則の意図的な転換
であるため、実装前にユーザーへ確認し、了承（「got it」）を得た。

**わかったこと（実画面で確認済み）**: SBIのログイン画面には、パスキー
（`https://login.sbisec.co.jp/login/entry` の「パスキー認証でログイン」ボタン）
とは別に、通常のID/パスワード欄（`input[name=username]` / `input[name=password]`,
送信ボタン `#pw-btn`）が同じページに存在する。ID/PWでの自動入力・送信自体は
問題なく行えるが、初回は送信後に `login.sbisec.co.jp/otp/entry` へ遷移し、
登録メールアドレス宛に送られる追加認証コード（OTP）の入力を求められた。
このブラウザでOTPを一度手動で完了させたところ、以降の同ブラウザからの
ID/PWログインではOTPを再度求められなくなることを確認した（デバイス／ブラウザ
単位で信頼されると見られる。ただしSBI側の正確な信頼期間・失効条件は非公開で
不明）。

OTP自体はメール受信箱へのアクセスが必要であり、これを自動で読み取って入力する
ことは「想定外の画面が出たら自動突破しない」という既存方針（パスキーと同じ扱い）
に反するため、意図的にスコープ外とした。

## Decision

- `sbi_client.py` に `_login()` を追加。`config/.env` の `SBI_USER_ID` /
  `SBI_LOGIN_PASSWORD` を使い、`https://login.sbisec.co.jp/login/entry` で
  ID/PWを入力して送信する
  - 送信後にログイン済みと判定できればそのまま復帰
  - `otp/entry` に遷移した場合は、そこで停止して `HumanInterventionRequired`
    を投げる（メールのコードをブラウザで入力するよう促すメッセージ付き）。
    パスキー同様、これ以上は自動で突破しない
  - 認証情報が `config/.env` に無い場合も、同様に安全側へフォールバックし
    （自動ログインを試みず）、従来通りパスキーでの手動ログインを促す
  - それ以外の想定外の画面になった場合も、本文スニペット付きで
    `HumanInterventionRequired` を投げる（他の全メソッドと同じパターン）
- `ensure_logged_in()` を、ログイン未確認時に `HumanInterventionRequired` を
  即座に投げていたところから、`_login()` を試みるように変更
- `ensure_logged_in()` 自体も修正: 従来は「既に `sbisec.co.jp` にいれば
  遷移しない」実装だったが、ログアウト直後の画面（`_ActionID=logout` の
  完了画面）はDOMに「ログアウト」という文字列が残ったままになっており、
  `_is_logged_in()` がこの古いDOMを見て誤って True と判定することを実際に
  確認した。これでは本当にログアウトしていても `_login()` に到達しない
  （＝自動再ログインが機能しない）ため、`ensure_logged_in()` は毎回必ず
  `HOME_URL` へ遷移してから判定するように変更した
- 既存の全呼び出し元（`web.py` の各処理）は `ensure_logged_in()` を呼んで
  `HumanInterventionRequired` を catch → `_alert_login_needed()`（Slack +
  macOS通知）という構造を既に持っていたため、`web.py` 側の変更は不要だった

## Verification（実画面で確認済み、2026-08-18）

- ID/PWでの自動ログインを実行 → 初回は想定通り `otp/entry` へ遷移し、
  `HumanInterventionRequired` が正しく送出されることを確認
- ユーザーが手動でOTPを完了 → ログイン成功を確認
- ブラウザで明示的にログアウト（`ensure_logged_in` を経由せず直接ログアウト
  リンクをクリック）→ 同一接続のまま `client.ensure_logged_in()` を呼び出し、
  自動でID/PWログインが成功し、**OTPを求められることなく**ログイン済みに
  復帰することを確認（デバイス信頼が効いていることの裏付け）
- `ensure_logged_in()` の毎回HOME_URL遷移への変更後も、ログイン判定が正しく
  動くことを確認

## Consequences

- 通常のログアウト（無操作によるセッション切れ等）は、人間の介入なしに自動で
  復旧するようになった。パスキー操作の頻度が大きく減る見込み
- OTPが必要になるケース（デバイス信頼が切れた場合など、条件は不明）は引き続き
  Slackアラート経由で人間の対応が必要。この場合はメールのコードを普段の
  ブラウザ側画面に直接入力してもらう（このツールはメールにはアクセスしない）
- `config/.env` にログインパスワードも平文で保存することになり、認証情報の
  漏洩リスクは（取引パスワードに加えて）ログインパスワード分も増える。
  `config/` はこれまで通り `.gitignore` 済み・`chmod 600` で運用する
- `ensure_logged_in()` が毎回 `HOME_URL` へ遷移するようになったことで、
  ログイン確認だけを目的とした遷移が1回増えた。`docs/adr/0011` の結論
  （通常運用レベルの遷移頻度自体は不安定化の原因ではない）を踏まえると
  実害は無いと判断しているが、念のため今後も不安定化の兆候があれば
  この変更を疑って良い
